Start here

Three buckets. If you can name which bucket a request is in, you know who owns the change. The nine widgets on the SAP “Composable Storefront Components” page are not the full SmartEdit catalog — they are shared UI building blocks. See Not only these nine.

Reuse as-is Edit in SmartEdit New code
Who UX / FE uses the OOTB widget Business / merchandising FE + often BE/CMS type
Typical ask “Put a banner / carousel / table on this page using the standard control.” “Change the image, headline, link, which widget sits in which slot, hide a component.” “After VIN, only show packages this dealer turned on.” No CMS type exists for that logic.
Deploy? Already in the library No storefront deploy Yes — Angular mapping, maybe ImpEx + OCC

SmartEdit edits content and placement of existing CMS types. It does not invent new behavior. If OCC does not return a field, SmartEdit cannot show it.

Rules to keep

  1. Copy, image, URL, show/hide, slot → SmartEdit (or ImpEx for initial load). No feature story needed for “swap the homepage banner.”
  2. Same CMS type, different look → reuse the component, restyle with CSS / styleClasses, or map the type to a custom Angular class. Do not clone Banner into five CMS types unless the data is actually different.
  3. New business rule (VIN eligibility, dealer catalog visibility, consent gating) → new component and usually a new CMS type or a non-CMS page that still uses shared primitives (table, pagination, popover).
  4. One Angular component can serve many CMS types. All banner types already map to one BannerComponent. Mirror that pattern instead of forking.
  5. Searchbox is product catalog only. It will not find coverage packages, VINs, or dealers. Do not promise typeahead for those without new code.
  6. Banner is not video. Known limitation: images and SVG only.
  7. Product media ≠ banner media. PDP/cart use product formats (thumbnail, zoom). Banners use content formats (mobile, tablet, desktop, widescreen) uploaded in CMS.
  8. Slots are the page skeleton; components fill them. Layout changes (new row on homepage) are CMS page structure. Pixel tweaks are CSS.
  9. Config in code still needs a developer — maxProducts on search, carousel itemWidth, pagination structure, table cell renderers. SmartEdit does not edit those TypeScript configs.
  10. Prototype ≠ production. Demos on this page are HTML stand-ins. Production widgets live in composable storefront (cx-media, cx-pagination, etc.).

How a page is built

Customer hits a URL → storefront asks OCC for the CMS page → backend returns slots and component payloads → each typeCode is mapped to an Angular component → that class renders.

SmartEdit authors the CMS page: which components sit in Section1 / Section2 / header slots, and the fields on each instance (headline, media, URL).

Developers own the mapping (cmsComponents: { BannerComponent: { component: … } }), guards, styling placeholders (%cx-banner), and any service logic.

Not only these nine

The SAP page you shared is a landing page for shared UI widgets, not a list of every CMS type you drag in SmartEdit. Several of those nine never appear as a CMS type at all — they are used inside other components.

On the SAP Components page Placed in SmartEdit as its own CMS type?
Banner, Searchbox Yes — you drop them on a page
Carousel Usually no — used by Product Carousel, Product References, rotating banners, PDP images
Media No — used inside banners, PDP, cart line items
Pagination, Popover, Table, Split view, Password visibility No — form/list chrome. You reuse them in code; merchandisers do not add “a pagination” to the homepage

    What else is easy to miss

    i18n

    Labels on OOTB components are translation keys, not SmartEdit rich text. New strings need a locale file (and often a CMS field if business must edit them without a deploy).

    Guards

    CMS mapping can attach Angular guards (logged-in only, consent approved, etc.). That is code. SmartEdit cannot “require login” on a component unless a guard already exists.

    SSR

    Some mappings set disableSSR. Personalization that differs per dealer/VIN may need a client render so the cached HTML is not wrong.

    ImpEx vs SmartEdit

    ImpEx seeds catalogs and sample banners in lower environments. Day-two content changes belong in SmartEdit so they survive builds.

    OCC contract

    The storefront only shows fields the CMS API returns. A “Show after VIN” flag that lives only in a dealer back office must be on an API the listing page can read — SmartEdit on the homepage cannot see it.

    Accessibility

    Pagination, popover, and split view have keyboard behavior already. Custom coverage cards should match that bar (focus, names, not div-click-only).

    Styling hook

    Prefer placeholder selectors and CMS styleClasses over a new component type when the only change is visual.
